# HyperFrames AI 导演工作台升级说明

更新日期：2026-09-06
项目版本：V4.0.1（本轮为能力升级，尚未单独提升版本号）

## 1. 这次改动解决什么问题

本轮改动把 HyperFrames 从“可以手动摆放动画积木的编辑器”，推进成一条有导演约束、有生产步骤、有质量门禁、能冻结版本并稳定交付的 AI 视频生产线。

过去的问题不是工具数量少，而是各个工具之间没有共同目标：内容生成、配音、素材匹配和导出可以分别运行，但它们不知道视频最终要对谁说、表达什么，也缺少统一的完成标准。工程即使能播放，也不代表已经达到可交付状态。

本轮围绕这个断点建立了五层能力：

1. 导演决策层：定义视频为什么存在。
2. AI 生产流程：按真实工程状态推荐下一步。
3. 声音驱动时间轴：用真实配音时长重排场景。
4. 项目体检：在最终导出前发现结构和媒体问题。
5. 发布候选与确定性渲染：冻结一个明确版本，再从该版本生成成片。

## 2. 当前完整工作流

```text
导演 Brief
   ↓
口播稿 / 场景计划 / 商品素材
   ↓
生成场景、字幕和配音占位
   ↓
批量生成真实配音并重排时间轴
   ↓
导入或自动匹配画面素材
   ↓
人工校正，锁定确认过的场景
   ↓
项目体检
   ↓
冻结 RC-001 / RC-002
   ↓
确定性渲染 MP4 或导出剪辑交付包
```

这条链路的核心变化是：最终成片不再来自一个随时变化的编辑状态，而是来自一个已经通过体检、不可变的发布候选版本。

## 3. 主要新增能力

### 3.1 导演决策层

新增工程级 `DirectorDecision`，记录：

- 传播目标
- 核心受众
- 核心表达
- 内容类型
- 语气和节奏
- 情绪弧线
- 结尾行动
- 视觉原则

每个场景还可以设置叙事职责、场景意图、视觉规则和锁定状态。场景锁定后，自动生成、字幕重建、批量配音和素材自动匹配不能覆盖该场景。

导演决策会进入自动保存、JSON 工程文件、发布候选和剪辑交付包，不再只是一次性提示词。

主要文件：

- `src/types.ts`
- `src/lib/directorDecision.ts`
- `src/components/agent/DirectorDecisionPanel.tsx`
- `src/lib/directorAgent/directorAgent.ts`

### 3.2 AI 视频生产线

AI 助手顶部新增四步生产面板：

1. 建立内容与时间轴
2. 锁定声音节奏
3. 补齐场景画面
4. 人工校正并交付

面板不是固定教程，而是读取当前场景、配音、素材和时长，判断工程现在位于哪一步，并给出下一项操作。原有实验工具被收进“高级工具与实验入口”，主流程更加集中。

主要文件：

- `src/components/agent/ProductionFlowPanel.tsx`
- `src/components/agent/AgentMenu.tsx`
- `src/components/agent/QuickGenerateButtons.tsx`
- `src/components/agent/WebCaptureLoader.tsx`

### 3.3 批量配音与声音驱动时间轴

生产线可以一次生成全部未锁定旁白。中文默认配音参数统一为：

- 音色：讯飞 `x4_lingyuyan`
- 语速：68
- 音量：56
- 音高：48

生成完成后读取真实音频时长，再同步调整场景、字幕、旁白和场景内画面。相同文案与声音参数会复用缓存；单项失败不会丢失其他成功结果；重排后支持一次性撤销。

主要文件：

- `src/lib/pipeline/batchVoiceover.ts`
- `src/components/agent/BatchVoiceoverPanel.tsx`
- `src/lib/pipeline/voiceover.ts`
- `src/lib/tts/index.ts`
- `server/xfyun-tts-proxy.ts`

### 3.4 项目体检与交付门禁

新增三类检查：

**阻断项**

- 工程为空
- 时间参数无效
- 场景互相重叠
- 图片或视频缺失
- 媒体仍依赖临时或外部链接
- 配音尚未生成
- 配音超出场景边界
- 积木引用了不存在的场景

阻断项会暂停最终 MP4 和剪辑交付包导出，但不会阻止 HTML 预览。

**制作风险**

- 场景没有主体画面
- 长场景只有一个画面
- 字幕没有对齐场景
- 单屏字幕过长
- 配音真实时长与时间轴不一致
- 素材库存在未使用素材

**导演一致性**

- 导演 Brief 不完整
- 已设置的场景缺少叙事意图
- 证据场景没有证据型画面
- 核心观点没有落到成片文案
- 结尾没有兑现设定的行动指令

体检问题可以直接跳到对应时间点并选中积木。字幕对齐和配音时长差异支持安全修复；被锁定的积木或场景不会被修复操作修改。

主要文件：

- `src/lib/projectHealth.ts`
- `src/components/agent/ProjectHealthPanel.tsx`
- `src/App.tsx`
- `src/components/agent/DeliveryPackageButton.tsx`

### 3.5 剪辑交付包

桌面版可以导出一个独立交付文件夹，内容包括：

- `manifest.json`
- `sceneplan.json`
- 独立图片文件
- 独立视频文件
- 独立配音文件
- 导演决策
- 每个积木的真实入点、时长、层级、位置和动画参数

交付包使用安全相对路径、自动规避危险文件名，并避免静默覆盖已有文件。它适合继续交给其他剪辑流程精剪，而不是只能留在 HyperFrames 内部使用。

主要文件：

- `src/lib/exportDeliveryPackage.ts`
- `electron/deliveryPackage.ts`
- `src/components/agent/DeliveryPackageButton.tsx`
- `electron/main.ts`
- `electron/preload.ts`

### 3.6 发布候选版本

体检没有阻断项后，可以冻结 `RC-001`、`RC-002` 等不可变版本。每个 RC 保存完整工程、媒体、导演决策和创建时的健康基线。

当前工作稿可以与任意 RC 比较：

- 新增、删除和修改了多少积木
- 场景结构是否变化
- 总时长变化
- 素材数量变化
- 制作风险变化
- 导演约束是否变化

候选版本保存在本机 IndexedDB，默认保留最近 12 个。恢复旧 RC 前会明确确认，恢复操作不会修改候选历史。

主要文件：

- `src/lib/releaseCandidate.ts`
- `src/components/agent/ReleaseCandidatePanel.tsx`
- `src/lib/persistence.ts`

### 3.7 RC 绑定的确定性 MP4 渲染

顶栏原“导出 MP4”入口改为“渲染 RC”。桌面版从指定 RC 生成自包含 HTML，然后使用浏览器逐帧截图和 FFmpeg 合成为 MP4。

渲染任务支持：

- 显示百分比和逐帧进度
- 收起面板后继续运行，重新打开可恢复状态
- 取消任务
- 失败后重试
- 取消或失败后清理临时半成品
- 音频统一输出为 48 kHz AAC
- 成功后打开输出文件

每次成功渲染同时生成 `.render-report.json`，记录：

- RC 编号和内部 ID
- RC 创建时间
- 工程和导演更新时间
- 分辨率、帧率和时长
- 渲染前健康基线
- MP4 文件大小
- MP4 的 SHA-256

最终文件因此可以追溯到明确的工程版本。

主要文件：

- `src/lib/releaseRender.ts`
- `electron/releaseRenderer.ts`
- `tools/html-to-mp4.mjs`
- `electron/main.ts`
- `electron/preload.ts`

## 4. 数据与安全原则

本轮实现遵守以下边界：

- 导演锁定优先于自动化操作。
- 发布候选只新增，不覆盖旧版本。
- 最终渲染只读取被冻结的 RC，不读取正在变化的工作稿。
- 渲染先写入带任务 ID 的临时文件，成功后才替换目标文件。
- 取消渲染会终止进程树并删除临时视频。
- 媒体数据和 RC 保存在本机，不自动上传到第三方服务。
- JSON、HTML、MP4 和剪辑交付包是不同用途的输出，不互相替代。

## 5. 使用方法

### 浏览器开发模式

```bash
npm run dev
```

浏览器模式可编辑工程、使用 AI 工作流、进行体检、管理 RC，并导出 JSON 或 HTML。浏览器模式不能直接写入本地 MP4 和剪辑交付文件夹。

### 桌面模式

```bash
npm run electron
```

桌面模式额外支持：

- 选择本地商品素材文件夹
- 导出剪辑交付包
- 指定 RC 直接渲染 MP4
- 打开渲染结果和交付文件夹

### 推荐操作顺序

1. 填写导演 Brief。
2. 导入口播稿或生成场景计划。
3. 批量生成配音并重排时间轴。
4. 导入并匹配图片、视频或网页素材。
5. 人工调整画面并锁定确认场景。
6. 打开项目体检，消除所有阻断项。
7. 建立首个 RC。
8. 如果继续修改，比较当前稿和 RC，再冻结新 RC。
9. 点击顶栏“渲染 RC”输出 MP4。
10. 需要外部精剪时导出剪辑交付包。

## 7. 当前明确边界

### 7.1 已支持数小时本地原片

长视频现在以本地路径引用进入工程，不再转成 Base64，也不会塞进自动保存或 RC。桌面版可生成 960px H.264 轻量代理用于源监看；时间轴只记录原片 ID、入点和出点，最终 RC 渲染会自动回到原片。

这解决了“两个小时素材把内存和工程文件撑爆”的问题，但并不代表系统已经能凭少量关键帧理解整段视频。用户仍需连续审片打点，或让外部转录/粗剪工具生成 EDL。

### 7.2 已有可执行的粗剪接口

“长视频源素材台”支持：引用多条本地原片、代理预览、源监看、设置入点/出点、把选段放入时间轴，以及导入通用 JSON EDL 批量生成连续粗剪片段。EDL 使用 `sources` 映射本地路径，`ranges` 记录 `source / start / end`。

逐词转写完成后还可以生成“可审粗剪候选”：系统按 0.45 秒级停顿拆分语句，并根据导演节奏使用 30–160ms 的安全边界。候选默认全部处于待审状态，不会自动改时间轴；用户可试听、查看画面、标记保留或排除。

保留片段进入独立的“导演结构编排”门禁。每段必须指定钩子、背景、核心步骤/观点、证明/结果、转折、结尾行动或自定义职责，并可脱离原片时间上下调整最终播放顺序。知识、产品、故事、教程和通用结构可一键预填，但预填不等于批准；用户仍须明确点击“确认这个结构”。只有职责完整、结构已确认、视觉检查通过、片段无重叠且导演 Brief 未变化，系统才会按导演顺序写入时间轴。

导演 Brief 更新后，旧编排自动判为过期。用户可以只同步新的目标、主旨和节奏，不丢失已经做出的保留/排除、视觉检查和排序决定，然后重新确认。候选策略、叙事职责、最终顺序与确认时间随工程保存并进入 `source-index.json`，本次追加可以整体撤销。

多条原片不再只能各剪各的。当两条以上素材产生保留候选后，可建立“跨原片故事装配”：候选以原片和精确入出点引用进入统一列表，在列表中跨机位调整顺序、统一分配导演职责，也可以只从全局故事中移除某段而不改变源素材审片结论。系统用文本相似度提示跨原片的重复表达，但提示不阻断执行、更不会自动删片。任一源候选或导演 Brief 发生变化时，全局确认自动过期；同步会尽量保留仍有效片段的顺序和职责。

全局装配必须再次明确确认，并继续服从逐段视觉检查门禁。执行时从当前播放头开始，按照全局顺序建立连续时间轴；整次装配可整体撤销。全局结构随工程、RC 和交付包的 `manifest.json` / `sceneplan.json` 保存。

正式写入时间轴前还有一层“结构预演”。桌面版按全局顺序把每段原片单独转为统一的 1280×720、24fps、低码率 H.264 片段，在画面左上角标记片段编号、来源和叙事职责，并在每段音频头尾应用 30ms 淡入淡出；随后使用 concat demuxer 无损拼接，不做第二次整片编码。无音轨素材会补静音轨，保证不同来源仍能稳定拼接。

预览会显示生成进度、支持取消、校验实际时长并按素材大小和修改时间缓存。用户可完整播放预览，并针对每个输出时间线切点生成九帧接触表，逐个标记“通过”或“需调整”。只有全部切点通过且用户明确确认整条预览，正式装配门禁才开放。任何排序、职责、源边界或导演上下文变化都会让旧预览失效。预演确认记录进入工程、RC、体检和交付包；已装配项目缺少有效预演凭证时，项目体检会阻止发布。

“需调整”不再只是一个死状态。切点卡片可直接把前段出点提前/延后 50ms，或把后段入点提前/延后 50ms；底层继续使用逐词边界和 30–200ms 安全余量，修改后清除该源候选旧视觉结论。切点前后片段还可以一键交换。没有逐词时间码的 SRT、人工动作候选不会开放这些按钮，而是明确要求回源播放器修改。

全局片段列表提供可搜索的替换候选池，只显示尚未进入当前故事的已保留片段；替换保留当前位置的导演职责，不修改源候选的保留/排除状态。所有边界、交换和替换操作都会让旧结构确认与预览失效，需要再次确认。预览缓存已经细化到单片段：缓存键包含原片大小、修改时间、入出点、职责、来源标记和片段编号，修订一个切点后只重编码受影响片段，其余片段直接复用，再无损拼接新预览。

导演可以在任何结构完整的阶段冻结一个不可变粗剪方案，系统依次命名为“方案 A、方案 B……”，并保存可选的修订理由。方案快照包含全局编排、每段来源、文本、叙事职责、精确入出点和当时的预演记录，但不会复制原视频。相同结构不能重复保存为新方案，避免版本列表被无意义快照淹没。

任意两个方案可以比较：新增/移除片段、共同片段换位、职责变化、边界变化、同一位置替换、总时长差和来源数量差。恢复前逐项验证源素材、候选 ID 和“保留”状态；任何候选丢失或已排除都会中止恢复。恢复时只把方案内记录的边界写回对应候选，保持所有 keep/drop 判断不变，也不会删除或覆盖正式时间轴。边界与当前值不同时清除旧视觉结论，恢复后的全局结构一律重新确认和预演。

两个方案都带有已确认预览时，可进入 A/B 导演选版。界面并排注册并播放两条本机预览，支持同时播放/暂停、按左侧或右侧相对进度同步，也会根据各方案片段累计时长计算叙事职责起点，一键把两条预览同时跳到共同的钩子、背景、核心、证明、转折、结尾等位置。这样比较的是相同叙事任务，而不只是相同秒数。

指定胜出方案时，胜出理由和另一方案的淘汰理由都是必填项；没有完整确认预览的方案不能参加最终选版。选版结论独立于方案快照保存，包括胜出方案 ID、实际比较的两个版本、理由、淘汰理由和选定时间。它不会自动改写时间轴，导演仍需主动恢复胜出方案并重新完成视觉检查、结构确认、预演和正式装配。

项目体检新增四类交付阻断：存在多个方案但未选版、胜出方案不存在或缺乏评审依据、当前全局结构与胜出方案不一致、胜出方案尚未正式装配。RC 冻结时把胜出方案 ID、标签、胜出理由和选定时间提取为只读 `storyDecision`，RC 对比也会单独提示导演选版是否发生变化；交付包的 manifest、sceneplan 和 release 追溯记录均携带这层信息。

对标记为保留的候选，桌面版只在用户点击时生成 3×3 视觉接触表：入点、正文中部和出点各取前/中/后三帧，并显示同一时间窗的局部波形。它不是全片关键帧扫描。视觉图缓存在应用数据目录，不膨胀工程 JSON；工程只保存审片状态。所有保留片段都必须标记“画面与边界通过”后，确认追加按钮才会开放。

如果边界画面不合适，逐词候选可以在 30–200ms 安全范围内按 50ms 调整前后余量，任何调整都会清除旧视觉结论并要求重新检查。外部 SRT/VTT 只有分段时间码时不提供伪精确微调。粗剪已经写入时间轴后必须先撤销，才能改动候选决定，避免审片清单与实际时间轴失配。

无台词动作不走全片关键帧识别。用户在源播放器连续观看后打入点/出点，并保存为“普通动作、重点保留或明确不要”。普通动作进入待审；重点动作默认保留且视为已人工看过；排除区间会把重叠语音候选置为排除。若人工动作边界落在一个词内部，系统会向外吸附到完整词边界。所有保留候选之间执行完整重叠检查，存在冲突时禁止写入时间轴。

外部原片选段默认保留现场声音并关闭逐段入场动画。最终 RC 渲染会按 `sourceIn/sourceOut` 抽取对应音频，每个边界增加 30ms 淡入淡出，再按时间轴混音。同一原片的多个选段共享一次 FFmpeg 输入并使用独立滤镜脚本，避免长粗剪因重复路径和超长命令行失败。

当前没有直接解析剪映私有草稿格式；建议先从剪映或 video-use 转成通用 EDL，再进入 HyperFrames。HyperFrames 负责导演结构、包装、版本和交付，剪映仍可负责更细的人工修剪。

胜出方案现在也能反向交给外部精剪。只有“当前结构就是胜出版本”且已经正式装配时，界面才开放精剪交接导出。交接数据以胜出方案的不可变片段记录为准，逐段写出素材别名、原片入出点、成片累计入出点、叙事职责和口播文本，并同时生成标准 JSON EDL、带 UTF-8 BOM 的 CSV 与成片时间线 SRT。

桌面端在创建目录前重新探测全部原片：检查路径、文件类型、字节大小、实际时长和切点范围，并为每条原片生成“大小 + 首尾各 1MB”的 SHA-256 快速指纹。任意检查失败都不会留下半成品交接目录。生成的包还包含 `sources.json`、`winner.json`、`verification.json` 和 `README-剪映交接.md`；它默认只引用原片，不复制数小时视频。这里明确不生成依赖版本的剪映私有草稿，`edl.json` 是可长期验证的剪辑决定主记录。

精剪回程也已闭合。导出的 EDL 额外保存来源方案 ID、素材 ID 和候选 ID；外部工具调整顺序、删除片段、修改切点或职责后，可以从选版区导回。系统先生成差异摘要，不直接修改时间轴；确认后创建带 `external-edl` 来源记录的新派生方案，原胜出方案保持不可变。来源版本错误、素材路径错版、重复引用、陌生新增片段、切点越界，以及有逐词时间码时切进词语内部，都会被明确阻止。派生方案必须按正常流程恢复、重检切点、预演并重新选版。

### 7.3 RC 已形成可追溯交付链

最终渲染完成后，成片路径、渲染报告、SHA-256 与完成时间会写回对应 RC。发布候选面板可导出指定 RC 的完整交付包，并生成 `release.json`，把 RC 身份、健康基线、审片汇总、最终成片和哈希绑定在一起。渲染凭证会持久保存，应用重启后仍能恢复。

### 7.4 长素材已有波形、本机转写与台词索引

桌面版可直接从原片音轨生成固定长度的波形缓存，点击波形跳转原片。源素材台现在会检测本机 `faster-whisper`、可用设备和已缓存模型，用户明确点击后在本机生成逐词时间码；任务有进度、可取消，素材未变化时复用缓存。仍支持导入带时间码的 SRT/VTT 作为外部转写。

这层能力只理解声音中说了什么，不会声称仅凭转写就理解所有烹饪动作。HyperFrames 负责台词索引、搜索、按词边界选段和版本交付；无台词动作仍需要波形审片、人工标记或后续视觉分析。波形、转写、逐词时间码和转写元数据会进入工程快照与交付包中的 `source-index.json`。

### 7.5 尚未完成的工程能力

- 完整的多步撤销/重做
- 出场动画和可视化关键帧曲线
- 无台词动作的视觉语义索引
- 从平台发布数据回流到导演决策
- 外部工具新增片段的受控纳入与来源审查
- 前端代码拆包和首屏性能优化

## 8. 下一阶段建议

标准交接和精剪回写已经形成往返闭环，下一阶段应处理“外部新增内容”和更强的时间线互操作：

1. 为外部新增片段提供待审收件箱，先映射原片、生成候选并做视觉/音频边界检查，再允许进入派生方案。
2. 支持 OTIO 或 FCPXML 等更完整的公开时间线格式，保留轨道、转场和速度信息。
3. 提供可选的剪映版本适配器，但始终以标准 EDL 和校验报告作为可验证主记录。
4. 对派生方案建立“导演胜出 → 外部精剪 → 最终 RC”的可视化血缘图。
5. 把发布后的留存、完播和评论信号回流到导演决策，而不是只记录播放量。

这会让 HyperFrames 保持自己的核心优势：它不需要替代剪映处理所有原片，而是成为决定内容结构、控制 AI 行为、管理版本并保证最终交付一致性的导演工作台。
